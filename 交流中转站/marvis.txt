## 项目定位
面向 GIS 初学者的自然语言制图与数据处理代理。寄生 QGIS Portable，双模式运行。

## 模块地图
```
src/ui/main_window.py       — 主窗口 DockWidget，信号/槽 → ai_worker
src/core/ai_worker.py        — 在线模式调度引擎 + system prompt + pipeline 解析
src/core/sandbox_worker.py   — PyQGIS 代码安全沙箱 (QThread + monkey-patch)
src/core/fallback_utils.py   — 确定性水文降级库 (numpy+gdal, 5算法+1全链路)
src/core/instruction_mapper.py — 离线模式关键词→22条指令映射
src/core/output_persistence.py — 输出路径管理 → user_data/exports/shapefiles/
src/skills/skill_manager.py  — 技能注册/路由/执行
src/skills/spatial_analysis_skill.py — 自由代码技能 + strict_find_fields
src/knowledge/gis_reference.py — PyQGIS/GDAL API 知识库
```

## 核心接口标准（已钉死，修改须 Solo 批准）
- fallback 水文函数：输出以返回值为准（actual_path），不依赖传入 output_path
- sandbox 降级路由回传：必须传 actual_output
- _resolve_paths()：空字符串视为缺失并继续兜底（刻意容错）
- generate_output_path()：user_data/exports/shapefiles/ 为权威输出目录
- _safe_create_output()：全部 5 个水文函数统一调用

## 宪法第九条 — 输入类型多态守卫 (2026-06-22, Solo 裁定)
QA 管线中 step A 的 engine fallback 从 qgis_processing 降到 shapely_wkt 后，
产出 StepResult(shapely_geom=..., qgis_layer=None)。Step B 引此时拿到 Shapely 对象。
若 Step B 引擎只支持 QgsVectorLayer 输入，会导致无声失败。

永久规则:
1. 引擎输入提取：先 _extract_shapely_geom，再回退 _extract_qgis_layer。
   禁止直接假设输入是 QgsVectorLayer。
2. StepResult 必须同时填充 shapely_geom 和 qgis_layer（如有），不可只填一个。
3. _extract_shapely_or_layer() 为统一入口，所有新引擎方法必须使用。
2. sandbox processing.run() monkey-patch 返回值漂移风险
3. _safe_create_output 锁判定仅英文异常消息，中文系统可能漏判

## SESSION RECORD — Phase 4 任务2：SaveAsProjectSkill 诊断 (2026-07-08)

### Solo 的断言
「skill_manager.py 扫描每个模块时只取第一个类，SaveAsProjectSkill 不是模块中第一个类 → 永远不会被扫描到」

### Marvis 诊断结论：Solo 的根因判断有误

**证据** — skill_manager.py L32-38：
`python
for attr_name in dir(module):
    attr = getattr(module, attr_name)
    if (isinstance(attr, type) and issubclass(attr, BaseSkill) and attr is not BaseSkill):
        instance = attr()
        self._skills[instance.get_name()] = instance
`

该循环遍历模块的**全部**属性，注册**每一个** BaseSkill 子类，不存在"只取第一个"的 break 或 early return。
两个类都会被注册：
- SaveProjectSkill → key: "save_project"
- SaveAsProjectSkill → key: "save_as_project"

### 真正的根因：缺失 NL 路由

template_registry.py 中只有一条保存相关条目：
`
"zh": ["保存项目", "保存工程"] → action: "save_project" → handler: _handle_save_project
`

不存在以下触发词的路由：
- "另存为"、"保存副本"、"保存为新文件"、"导出为新项目"
- "save as"、"save as new"、"save copy"

SkillManager 注册了技能，但自然语言入口缺失——用户说"另存为"时 keyword_pre_match 匹配不到，路由链路断裂。

### 修复方案

在 template_registry.py 的 _INSTRUCTION_TEMPLATES 中新增一条：
`python
{
    "action": "save_as_project",
    "zh": ["另存为", "保存副本", "保存为新文件", "导出为新项目"],
    "ja": ["名前を付けて保存", "別名で保存"],
    "en": ["save as", "save as new", "save copy"],
    "handler": "_handle_save_as_project",
},
`

同时需要在 handlers_basic.py 中新增 _handle_save_as_project handler（包装 SkillManager.execute_skill("save_as_project")），并在 instruction_mapper.py 的方法表中注册。

影响范围：3 个文件，预计 +25 行。

building_risk boundary_layer 占位文本防御

## 现象
CEO 测试建筑倒塌风险分析时 AI 回复：图层 '边界图层名(可选)' 未找到

## 根因
building_risk.json 模板中 boundary_layer 参数注释为"行政区边界图层（可选，用于裁剪到想定区划内）"。
LLM 将注释语义中的"可选"理解为参数值，将"边界图层名(可选)"作为 boundary_layer 传入 handler。
handler 未做防御，直接传递给 PipelineExecutor → _find_layer 找不到该名称 → 报错。

## 修复
handlers_analysis.py _handle_building_risk_analysis() 中，在 boundary_layer 传入 executor 之前增加占位文本检测：

`python
# 防御：LLM 可能将模板占位文本（如"边界图层名（可选）"）当作参数值传入
if boundary_layer and not self._find_layer(project, boundary_layer):
    _placeholder_keywords = ["可选", "图层名", "不填", "图层名称", "边界名称"]
    if any(kw in boundary_layer for kw in _placeholder_keywords):
        _log.info("boundary_layer 疑似模板占位文本'%s'，视为未提供", boundary_layer)
        boundary_layer = ""
`

改动范围：handlers_analysis.py +7 行（在 L327 intensity_field 探测块之后、template_path 之前）
影响：仅 building_risk 分支，无 API 变更，完全向后兼容
安全：仅当 layer 不存在且匹配占位关键词时才视为未提供，不会误伤真实图层

[TO_SOLO] Codex 审查 第 2 条 — 覆盖分析全链路故障分析

用户输入：'帮我做学校500米覆盖分析'
链路：意图识别 → 图层选择 → 参数提取 → 守卫检查 → Pipeline 8步执行 → 结果呈现

# 步骤0：入口校验（handler 层）— 临界故障
- _handle_coverage_analysis L226: if not source_layer or not boundary_layer → 直接拒绝
- 任何空字符串/None/空列表都触发。即使后续步骤全对，卡在这一步就死。

# 步骤1：意图识别 — 风险中等

离线模式（本地7B LLM）：
- JSON提取三层容错（直接解析/代码块/花括号），单轮成功率约60-70%（经验值）
- keyword_pre_match 兜底：触发词包含'覆盖分析'，'学校500米覆盖分析'可命中 ✓
- keyword 纠偏：LLM返回非 coverage_analysis 时，触发词交叉校验可纠正 ✓
- 但触发词列表不包含'学校''避难所''基站'等业务场景词 → 完全依赖LLM

在线模式：
- 大模型理解能力好，但 radius_m=500 需从'500米'提取，可能遗漏
- 已知问题：LLM偶尔返回 spatial_join 而非 coverage_analysis（语义相近）
  → keyword 纠偏可修复

评估：在线模式风险低，离线模式风险中（JSON解析失败率~30%）

# 步骤2：图层选择 — ⚠️ 结构性缺陷（高故障率）

auto_detect_layers_from_text (template_registry.py L435-505):
- 遍历 layer_params 列表中的 source_layer / boundary_layer
- 但在匹配分配逻辑中，只有 target_layer / join_layer / layer_name / intensity_layer / population_layer 有特殊处理
- source_layer 和 boundary_layer 的 elif 分支缺失 → 永远不会被自动填充

LLM 也无法弥补：
- 离线模式 system prompt 未注入当前已加载图层列表
- LLM 只看到静态模板描述 '源点图层名'，不知道实际图层叫 'schools_3857' 或 '学校点位'
- 用户说'学校'但图层名是英文/带后缀 → LLM猜不对

实际结果链：
  user_text='帮我做学校500米覆盖分析'
  → auto_detect: found_names=['schools_3857']（仅当图层名恰好出现在文本中）
  → source_layer=''（未匹配），boundary_layer=''（未匹配）
  → handler 收到空值 → 步骤0拒绝 ✓ 直接报错

故障率估算：用户不逐字说出图层名时 >80% 失败

# 步骤3：参数提取 — 风险低

- radius_m: 模板默认500.0，LLM无需传 → 默认兜底 ✓
- '500米'→500 在LLM能正确提取的情况下没问题
- selected_only: 默认False，忽略

评估：有默认值兜底，风险低

# 步骤4：守卫检查 — 风险中

coverage_analysis.json guards:
- crs_projected: 源图层是 EPSG:4326→失败
- source_is_point: 非点图层→失败
- boundary_is_polygon: 非面图层→失败
- boundary_fc_limit: >10000要素→失败
- shapely_available: 未安装shapely→失败
- crs_match: auto_reproject=true → 跳过检查

关键问题：模板 guards 的 on_fail 未显式设置 → 使用 GuardCheck 默认值 'warn'
→ guards 失败时仅记录警告，不阻断执行

当 crs_projected 失败（EPSG:4326）时：
- 不阻断，继续执行
- buffer步骤用度做单位 → 500度缓冲区 → 结果错误但无报错
- 或 QGIS processing 直接静默返回 0fc → 后续步骤 cascade 失败

评估：crs_projected 仅warn不阻断 + 无自动重投影 → 风险中高

# 步骤5：Pipeline 8步执行 — 逐步风险

1. boundary_dissolve (QGIS dissolve, 无fallback):
   - 大坐标下QGIS可能静默返回0fc → 后续缓冲区无边界 → stats area=0
   - 无 Shapely fallback ⚠️

2. boundary_buffer (QGIS buffer, 无fallback):
   - 同上，大坐标静默0fc → spatial_filter无输入 → 全链路崩塌
   - 无 Shapely fallback ⚠️

3. spatial_filter (QgsSpatialIndex):
   - 依赖QGIS内部实现，大坐标下bbox计算可能异常
   - 风险：中低

4. buffer (QGIS + Shapely fallback): ✓ 双重保障

5. dissolve (QGIS + Shapely fallback): ✓ 双重保障

6. clip (QGIS clip → intersection → Shapely WKT): ✓ 三级fallback

7. stats (Shapely area): ✓ 最稳定

8. output_layer (内存图层 → GeoJSON fallback): ✓ 双重保障

评估：步骤1-2 无 fallback 是薄弱环节，大坐标场景下静默失败

# 步骤6：结果呈现 — 风险低

- PipelineExecutor.execute 返回 dict 含 stats（coverage_rate, covered_area 等）
- output_layer 步骤自动 add_to_project + zoom_to_layer
- handler 直接转发返回值
- canvas 参数在 handler 层有传递 ✓

评估：风险低

# 综合诊断

致命级（当前必挂）：
- 步骤2 auto_detect 不处理 source_layer/boundary_layer → 图层名失配时100%失败
- LLM prompt 不含已加载图层列表 → LLM 无法猜测正确图层名

高风险：
- 步骤4 crs_projected 仅warn不阻断 → 地理坐标系下数值错误但无报警
- 步骤5.1-2 boundary_dissolve/boundary_buffer 无 Shapely fallback

中风险：
- 步骤1 离线模式 JSON 解析失败率~30%
- 步骤3 LLM 可能不传 radius_m（默认值兜底，影响可控）

# 可执行改造建议

1. 【紧急】auto_detect_layers_from_text 增加 source_layer/boundary_layer 分配逻辑：
   当 found_names 含2个图层时，按几何类型分配（点→source, 面→boundary）
   当 found_names 含1个图层时，让 LLM 补充或提示用户

2. 【紧急】coverage_analysis.json guards 显式声明 on_fail: 'error'
   或为 crs_projected 添加 auto_reproject 逻辑（类似 crs_match 的 auto_reproject）

3. 【推荐】boundary_dissolve 和 boundary_buffer 增加 Shapely fallback

4. 【推荐】离线模式 system prompt 注入当前项目已加载图层列表

5. 【可选】keyword 触发词扩充业务场景词（学校/避难所/基站/医院等）

[TO_SOLO] Codex 审查 第3条 — exec() 安全性、正确性、可重复性分析

在线模型生成 PyQGIS 代码后，经 SandboxExecutionWorker(QThread) 调用 exec() 执行。
执行路径：LLM 生成代码 → main_window 提取代码块 → SandboxExecutionWorker.run() → _safe_exec() → exec()

# 一、exec() 方案的实际限制

## 1. 不可中断
- QThread.cancel() 仅设置 _cancelled 标志，无法中断正在执行的 Python exec() 代码
- 无限循环或长时间运行的 processing.run() 会永久阻塞 Worker 线程
- 无超时机制：代码跑 10 分钟也不会被 kill

## 2. 无资源隔离
- 无内存限制：代码可申请任意内存
- 无 CPU 限制：无时间片/配额控制
- 无文件系统隔离：代码运行在真实文件系统中，可读写任意路径
- Python 原生 exec() 无法做沙箱级别的系统调用拦截

## 3. 无能力白名单强制执行
- SANDBOX_CORE_GLOBALS 注入预定义类（QgsProject/QgsVectorLayer 等）是"便利"而非"限制"
- LLM 代码可以通过以下方式绕过全局变量限制：
  - __import__('os') → 获得完整 os 模块
  - importlib.import_module('subprocess') → 获得 subprocess
  - type(QgsProject) 遍历 MRO 获取 object 基类 → 触碰 __subclasses__() 链
- 提示词禁止的模块（pandas/openpyxl/subprocess 等）没有在代码层面实施拦截
  → 代码中 import pandas 会因环境未安装而崩溃，但崩溃属于被动防御，非主动拦截

## 4. 状态不可回滚
- 执行前仅做图层 ID 快照（_snapshot_map_layers），不备份文件、不做事务
- exec 中途崩溃 → 可能留下半成品图层、文件
- GC 清理（_gc_cleanup）仅在成功路径执行，失败路径跳过

## 5. 结果不可重放
- 同一条代码执行两次可能得到不同结果：
  - QgsProject 状态已变化（第一次执行后 addMapLayer 了新图层）
  - 文件系统状态变化（第一次 generate_output_path 已占用路径 → 第二次覆盖或报错）
  - processing.run 的 "memory:" 输出在两次执行间不持久化

# 二、提示词约束 vs 实际防御

以下约束仅存在于 system prompt 文本中，代码层面无强制执行：

| 提示词约束 | 实际防御机制 | 可被绕过？ |
|-----------|-------------|-----------|
| 禁止 print/input/sys/subprocess/eval/exec/open/__import__ | 无代码拦截 | ✅ 直接写即可，提示词无强制力 |
| 禁止定义类和函数 | 无 AST 检查 | ✅ 完全可以定义 |
| result 必须赋值给 result | 无验证 | ✅ 赋给其他变量名也能通过 |
| 禁止 pandas/openpyxl/xlrd/csv | 环境未安装→崩溃 | ⚠️ 被动：崩溃阻止但无友好提示 |
| 禁止 grass7: | 算法不存在→崩溃 | ⚠️ 被动：QgsProcessingException |
| 禁止 iface | iface 不存在→NameError | ⚠️ 被动 |
| 禁止 TEMPORARY_OUTPUT/memory: | 无强制 | ✅ 用 memory: 也能跑，仅重启后丢失 |
| CRS 必须投影 | Pain 4 CRS 防御自动 reproject | ⚠️ 主动防御！但仅在 active_layer 非 None 时触发 |
| 必须调用 style_manager | 无检查 | ✅ 不调也能通过，图层落图但无配色 |
| 必须 try-except 包裹样式代码 | 无检查 | ✅ 不包裹也能通过，崩溃时连带图层丢失 |

# 三、已有的真实防御（值得肯定）

1. **CRS 防御（Pain 4）** — 自动以 active_layer 为基准 reproject 所有图层，地理坐标系自动升级 EPSG:3857
   → 有效防止"度当米用"类错误
2. **图层 GC（Pain 3）** — 执行前后快照对比，卸载中间图层
   → 三级白名单机制（deferred ID / result ID / 名称关键词）
3. **QThread 隔离（Pain 1）** — exec() 不在主线程，UI 不冻结
4. **自愈循环（Pain 2）** — SyntaxError/Exception → fix_needed 信号 → LLM 修正 → 重试（最多3次）
   → 实际有效！SyntaxError 基本 1-2 次修复
5. **Monkey-patch addMapLayer** — 拦截到 _deferred_layers，主线程安全加载
6. **processing.run() 降级路由** — 37 个水文算法自动路由到静态 numpy/gdal 实现
   → 有效防止便携版 QGIS 缺失算法的崩溃
7. **SandboxStdoutBridge** — print() 输出逐行透传到 UI 控制台
8. **水文管道自愈** — 检测到水文 fail pattern 后自动注入完整确定性管道

# 四、当前最危险的未防御风险（按危害排序）

## 🔴 风险1：文件系统无限制访问
- exec 代码可以直接 os.remove() 删除用户文件
- 可以直接 open(f, 'w') 覆盖任意文件
- 可以 shutil.rmtree() 删除目录
- 当前仅靠提示词约束，零代码拦截

## 🔴 风险2：进程/网络无限制
- subprocess.Popen / os.system / os.popen 可执行任意系统命令
- import requests / urllib 可发起任意网络请求
- 提示词禁止但无强制力

## 🟡 风险3：无超时/无中断
- 无限循环或长时间 processing 操作永久阻塞 Worker
- 没有超时 kill 机制
- 用户体验：UI 不冻结但"永远在运行中"

## 🟡 风险4：结果不可重放
- 同一代码两次执行结果不同
- 无执行前项目快照（QgsProject + 文件系统）
- 无法进行回归测试

## 🟢 风险5：exec 代码审计为空白
- 没有代码执行前的静态分析（AST 扫描）
- 没有危险调用检测（os.remove / subprocess / eval）
- 没有执行后的结果校验（result 必须存在、图层必须已加载）

# 五、可执行改造建议

## P0（安全底线 — 1天可完成）

## P1（可靠性 — 3天）

[TO_SOLO] — Codex 第5条：Template/Guard/Pipeline/Skill — 确定性执行 vs 补丁
提交时间：2026-07-12

【概念定义】
确定性执行：单一 primary engine，无 fallback，路径固定
补丁：存在 fallback 链 / validate 条件分支 / skip_if / auto_skip 标记

【Templates（31个）】
确定性（24个）：load_layer ~ filter_layer + export_* + add_label/open_field_manager/layer_statistic/create_buffer/spatial_join
混合（7个）：coverage_analysis / gap_analysis / population_coverage / building_risk / seismic_situation_map
→ 确定性占比 77%，但 7 个复杂模板是补丁密集区

【Pipeline JSON Steps — 补丁逐项审计】
coverage_analysis（8步）：
  确定性：boundary_dissolve / boundary_buffer / spatial_filter
  补丁：buffer（QGIS→Shapely fallback，大坐标下 buffer 返回 0）
        dissolve（QGIS→Shapely union fallback，大坐标下 dissolve 失效）
        clip（clip→intersection→shapely_wkt 三级链，大坐标下返回空）
        stats（强制 shapely area，QGIS area() 大坐标返回 0）
        output_layer（memory_layer→geojson_file，大坐标降级）
gap_analysis（9步）：+1 补丁 difference（纯 shapely_wkt，不走 QGIS）
population_coverage（9步）：+1 补丁 pop_intersect（纯 shapely_wkt）
building_risk（4步）：4/4 补丁（intensity_clip + pop_intersect + stats + output_layer）
→ 所有补丁根因 = QGIS processing 在 EPSG:3857 大坐标范围下几何运算不可靠

【Guards】
框架：GUARD_REGISTRY + GuardChecker 遍历 → 确定性
策略：on_fail 默认 "warn"（非 "error"）→ 补丁式宽松
crs_match auto_reproject→auto_skipped → 补丁式跳过
_guard_source_is_vector：return passed=True → 占位未实现

【Pipeline Executor 本身】
确定性：_parse_template / engine_chain 扁平化 / _execute_step / $ref 跨步传递 / 边界自动传播 / 结果汇总
补丁存在于 JSON 内容中，而非 executor 框架

【总结】
框架层（模板路由 / pipeline 声明式执行 / guard 注册表）→ 确定性，设计良好
补丁集中在执行层，根因高度集中：QGIS processing 大坐标 bug
若 QGIS 修复，6 个补丁步可直接裁掉 fallback 退化为确定性执行

二、根因诊断（按影响力排序）
────────────────────────────────────────────────────────

2.1 【主要根因】启动环境缺失 — 无测试引导脚本
   PyQt5 的 QtWidgets.pyd 在导入时会通过 Windows DLL 搜索链
   查找 Qt5Core.dll / Qt5Gui.dll 等。这些 DLL 位于：
     D:\桌面\AIQGIS_APP\qgis-portable\apps\Qt5\bin\
   而 portable Python 启动时并未将 Qt5/bin 加入 PATH。
   对比：系统安装版 QGIS 3.44.9 的 qgis-ltr-bin.env 中有
   完整的 PATH / QT_PLUGIN_PATH，但项目没有等效的测试引导。
   → 类别：启动环境问题（Launch Environment）

2.2 【次要根因】多 Python 版本冲突
   本机存在 3 套 Python：
   - Marvis 运行时：Python 3.11（D:\Program Files\Tencent\Marvis\...\python311\）
   - portable QGIS：Python 3.12（D:\桌面\AIQGIS_APP\qgis-portable\apps\Python312\）
   - 系统 QGIS 3.44.9：Python 3.12（C:\Program Files\QGIS 3.44.9\）
   默认 python 命令指向 Marvis Python 3.11，它没有 PyQt5/Shapely。
   必须显式调用 portable Python 或设置 PYTHONHOME。
   → 类别：PATH / Python 可执行文件选择

2.3 【辅助因素】无共享 conftest.py
   所有测试的 setUp / setUpClass 都没有调用 qgis_env.bootstrap_qgis()，
   test_image_preprocessor.py 直接 from PyQt5 import ... 在模块级执行，
   collection 阶段就崩溃，其他文件完全跑不到。
   → 类别：测试设计问题（Test Design）

2.4 【非根因】Shapely DLL 本身无问题
   Shapely 在 portable 环境中已正确安装（Python312\Lib\site-packages\shapely\），
   GEOS DLL 随包分发。实测中 Shapely 从未真正失败——
   只是 test_image_preprocessor 的 PyQt5 导入先崩了，
   test_population_coverage 根本没跑到 collection。
   → 类别：误报（False Positive by cascade failure）
